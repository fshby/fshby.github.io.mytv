# 河南卫视（107.150.60.122）电视端偶发卡顿分析

日期：2026-10-01 晚 · 设备：小米电视 MiTV-ASTP0（Android 9）· 对照：PC 端 VLC

## 一、结论摘要

这个源是**美国中转的网关型聚合源**，电视端偶发卡顿由三个叠加因素造成，全部有实测证据：

1. **跨洋带宽波动**：流需求 ~3.4 Mbps，同一网络直连实测下载速度在 5.2~9.6 Mbps 间波动（**富余 1.0x~2.8x**），晚高峰会贴到 1.0x —— 缓冲垫被击穿就是一次卡顿；
2. **网关轮换后端**：入口 302 跳转偶发落到**另一台分片时长完全不同（16.67s vs 7.6~10s）、序列号体系独立**的后端，播放器时间轴错乱一次卡顿；
3. **切台初期垫子薄**：实测起播 offset=10399ms（垫约 2 片），速度贴 1.0x 时首 1~2 分钟最脆弱。

**分片内容本身健康**（音频 96kbps 均匀、PTS 连续），不是梨园那种音频空洞问题。真机 210 秒播放日志**零 HTTP 错误、零 BehindLiveWindow、零音频错误**——卡顿不是报错型，是纯带宽波动 + 偶发后端切换型。

## 二、证据链

### 1. 网关结构（绕过本地代理直连取证）
```
http://107.150.60.122/live/hawshd.m3u8   (网关，US)
  └─302→ http://198.204.233.130:82/live/haws.m3u8?jsbt=<时间>&jsbk=<签名>  (后端A，US)
          窗口 3×10s=30s，seq≈483xx，分片 haws/segment_NNNNN.ts
  └─302→ http://173.208.146.10:88/applive/107.m3u8?u=<客户端IP>&t=<时间>&k=<签名>  (后端B，US)
          TARGETDURATION=17，分片 16.67s，seq≈207xx，分片 107/NNNNN.ts
```
- 连续 8 次请求全落后端 A（粘性为主），但 12 次采样中后端 B 出现过 1 次（~8%）；
- **token 实测 ≥8 分钟有效**（RedirectMemory「签名地址固化必然失效」的假设对此类源不成立，这是可利用的修复点）；
- 分片**必须带 token**（无 query 一律 404）。

## 三、为什么 VLC 不卡而 App 卡

1. **起播位置**：VLC 直播起播垫得更厚（基本贴满窗口），App 垫 ~2 片；跨洋速度贴 1.0x 时薄垫先被击穿，这正是「**刚切台后的一段时间**卡」的形态；垫子养起来后（30~60s）两者差距消失。
2. **playlist 刷新路径**：两者每轮都过网关 302，但 ExoPlayer 对后端切换（seq 突变、分片时长翻倍）的时间轴校验比 VLC 严格，一次错乱就是一次可感知的顿挫。
3. 偶发因素（后台切换、Wi-Fi 抖动）双方等概率承受。

## 四、修复建议（按性价比排序）

1. **RedirectMemory 扩展（推荐，改动小收益大）**
   - token 型落地地址改为「**一次学习即固化 + 失败自动回退网关**」（token ≥8min 有效，回退只多一跳 RTT）；
   - 顺带实现**后端粘性**：新落地 host 与记忆不一致时，自动重试网关 2~3 次取回同后端，杜绝后端轮换造成的时间轴错乱。
2. **低富余源加大垫片**：`headroom < 2x` 的源起播垫片取「窗口的 2/3」（本例 30s 窗口垫 20s），切台初期抗性翻倍。
3. **可选**：把这类美国中转源在国内中转一遍（自建反代），根治波动——成本最高。

## 五、勘误与边界

- **media3 实际为 1.2.1**（`libs.versions.toml` + 真机日志 `[AndroidXMedia3/1.2.1]` 双重核实；此前记忆中的 1.3.1 是错的，已修正）。
- 小米电视无 `curl`（烽火盒子有），本次电视侧取证能力受限，速度数据以同网络 PC 直连为准。
- 测试用的单频道列表已从电视删除，应用数据目录已还原。
