# 播放异常分析与兼容方案（完整复盘）

> 2026-09-30 ~ 2026-10-01，针对 fshby 定制版（v2.3.0 → v2.4.0）在真机上的四类播放异常，逐一定位根因并落地兼容方案。
> 取证环境：烽火 HG680-KF（Android 9）、小米电视 MiTV-ASTP0（Android 9），分析工具为流式 logcat、MPEG-TS 分片解析（PES/PTS 级）与源出口实测。

## 一、切台后前几个分片卡顿（2026-09-30）

### 1.1 根因链

- 旧代码在 `PlayerFragment` 里对所有源固定 `.setTargetOffsetMs(3000)`，覆盖了 media3 对 HLS 直播的默认偏移（3 × 目标时长）；
- media3 会把「直播边缘 − 偏移」**回退到最近的分片起点**——3 秒的偏移在 4 秒分片的源上直接落进最后一片，起播点身后只剩 1 片；
- 窗口滑动即滑出（`BehindLiveWindowException`）、带宽一抖即击穿缓冲，表现为切台初期周期性卡顿；
- 叠加 `DefaultLoadErrorHandlingPolicy` 对分片 404/502 仍按默认 0/1/2s 退避——一片坏 ≈ 冻结 3 秒。

实测 209 个可用源回算：**44% 的源窗口只有 2~3 个分片；源端下载速率与实时需求差 3 个数量级；分片级失败率 15~20% 且集中在窗口两端**——薄垫 + 短退避在这个源分布下必然"切台卡一下、再卡一下、然后好了"。

### 1.2 兼容方案（全部落地，`c8d779b`）

1. **起播偏移按源画像**（`SourceProfile.targetOffsetFor`）：
   - 剔除 0 时长分片 → 目标垫片 ≈ 2 个平均分片，钳 `[6s, 30s]` → 在「下标 ≥ 1（身后至少留 1 整片）」内取垫片不超过目标的**分片起点**；
   - 回算收益：起播可垫内容中位 6s → 10s；「至少垫 1 片」92 → 170 源；「贴窗口最旧片」6 → 0 源。
   - 关键实现事实（media3 1.2.1 源码核实）：`HlsMediaSource.updateLiveConfiguration()` 只写 `targetOffsetMs`，`min/maxOffsetMs` 被丢弃不钳制——所以只设 targetOffsetMs 即可同时决定起播位置和追赶目标。
2. **分片级错误短退避**（`MyLoadErrorHandlingPolicy`）：分片 404/502/超时/IO → 固定 300ms × 4；playlist 级 400ms 递增；解析类错误致命。
3. **探测升级三段式**：`probeHead`（复用 4096B 预读）→ `parseHls`（目标时长/窗口/分片，master 按 BANDWIDTH 下钻）→ `measureSpeed`（384KB/1s 限量预算，倒数第 2 片实测）。
4. **多源按质量排序**：小窗口降权 → 富余倍数 → 实测速率 → 建连耗时，保留前 2。
5. **直连 TS 流兜底**：解析不出 HLS 但过存活校验的源留末位备用，避免整条频道消失。
6. 画像落盘（`cache/mytv-sources.txt`）：跳过探测的那次启动同样有偏移可用。

**真机验证（烽火 HG680-KF）**：`play CCTV1 offset=20000ms`、黑龙江 14019/10000/6021ms 随源变化；FATAL=0、BehindLiveWindow=0，3 次 Source error 均被瞬态重试接住。冷启动探测 262 频道 77 秒，二次启动 304 跳过探测。

> 衍生问题：盒子时钟停在 2009 → Let's Encrypt 证书判未生效 → HTTPS 列表彻底拉不下来。随 `25a14ad` 落地**内置快照兜底 + 时钟偏斜检测提示**（三场景真机验证通过）。

## 二、梨园频道：源端音频空洞（2026-09-30）

### 2.1 取证

用只含梨园的临时列表定向复现，流式抓取 110 秒：

```
play 梨园 offset=8000ms
E/MediaCodecAudioRenderer: Audio sink error   ← 起播 1.75s 即开始，110s 内 38 次，与分片周期(4s)同步
Caused by: BehindLiveWindowException          ← 47s 后滑出窗口
```

异常正文 `AudioSink$UnexpectedDiscontinuityException: expected ..., got ...`，差值 0.96~2.20s。

下载真实分片做 MPEG-TS 解析（PES/PTS 级）：

| 指标 | 梨园 lypd | 河南曲艺 jczy（同主机对照） |
| --- | --- | --- |
| 视频轨道 | 100 PES/片，PTS 严格 4.0s/片连续 | 正常 |
| 音频 PES / 4s | **2~4 个** | **10 个** |
| 音频码率 | **6.6~20 kbps** | **69 kbps** |
| 音频载荷占比 | 0.55~1.27% | 2.49% |
| PES 间隔 | 0.5~3.3s 空洞 | 均匀（约 2.8KB/个） |

**结论：主因是源端音频轨道有空洞**（视频完全正常），播放器每读一个新分片就撞一次音频时间戳跳变、重建音频输出；App 侧偏移算法又把起播点钉在离边缘只剩一片处（3 片窗口 + 末片 8s 时「不超过目标」约束反而选中末片），放大了滑出频率。

### 2.2 兼容方向

1. 偏移算法：无候选满足「≤ 目标」时回落**最旧片**而非末片（见第六节遗留）；
2. `tinyWindow` 判据扩展到 `segments ≤ 3`，短窗口源在多源排序中降权（只降权、不剔除）；
3. 治本规划：探测期音频体检（音频码率 <30kbps / 载荷 <1.5% / PES <5 → 标记降序）；
4. 明确不做：丢频道（视频正常）、调 buffer 参数（对音频空洞无效）、磁盘媒体缓存（分片带鉴权一次性）。

> 注意：`UnexpectedDiscontinuityException` 阈值是 media3 内部常量，无公开 API 可调；这类源端缺陷客户端只能规避/提示，无法修复。

## 三、河南卫视：网关型源三种卡顿形态（2026-10-01）

### 3.1 源结构（直连取证）

```
http://107.150.60.122/live/hawshd.m3u8        （网关，美国机房）
  ├─302→ 后端A 198.204.233.130:82   窗口 3×10s，seq≈483xx，落地带 jsbt/jsbk 时间签名（≥8min 有效）
  └─302→ 后端B 173.208.146.10:88   分片 16.67s，seq≈207xx（独立序列号体系，偶发 ~8% 落此）
```

### 3.2 三种卡顿形态（全部实测确认）

1. **跨洋带宽波动**：流需求 3.4Mbps，同网络实测 5.2~9.6Mbps（富余 1.0~2.8x），晚高峰贴 1.0x——垫子被击穿就是一次卡；
2. **后端轮换**：偶发落到后端 B → 序列号突变 + 分片时长翻倍 → 播放器时间轴错乱一次顿挫；
3. **切台初期垫片薄**：起播垫 ~2 片，链路贴线时首 1~2 分钟最脆弱。

**为什么 VLC 不卡**：VLC 直播起播垫得更厚（基本贴满窗口）、对后端切换的时间轴校验更宽容。分片内容本身健康（音频 96kbps 均匀、PTS 连续），真机 210s 播放零 HTTP 错误——是纯带宽波动 + 偶发后端切换型，不是报错型。

### 3.3 兼容方案（`a1f91b5`）

1. **RedirectMemory：token 型落地一次学习即固化**——落地 URL 带时间签名，旧逻辑「连续两次一致才确认」永远不成立，每轮 playlist 刷新都过网关 302，偶发轮换后端。现在 token 型（`query != null`）第一次学到就固化直连，整个会话锁定同一台后端（**后端粘性**）；
2. **失败就地回退**：固化地址直连失败 → 原地重走网关拿新 token（播放器无感知，不触发 LoadErrorHandlingPolicy）；曾成功过的条目失败 = token 过期，回退即重新固化，粘性无缝续期；**从未成功过** = 一次性 token，拉黑 10 分钟，零额外损耗。静态 CDN 地址保留两次一致确认。
3. **低富余源加大垫片（伪实时模式）**：探测实测 `kbps < 2 × demandKbps` 的源，起播垫片 = max(2×平均分片, **窗口 2/3**)，仍钳 [6s,30s]——接受更大的起播延迟（约落后直播边缘 10~20s）换取波动期不击穿缓冲。

**真机验证（小米电视）**：清数据重新探测后 240s 定向播放：`play 河南卫视 offset=11120ms`，**0 Source error / 0 BehindLiveWindow / 0 掉帧 / 0 重缓冲暂停**；三台后端（198.204.233.130:82 / 173.208.208.10:82 / 204.12.224.154:88）各自整场粘住。

## 四、运行时重缓冲反馈（2026-10-01 深夜）

终验时发现河南卫视仍卡：探测排序选中了另一条「快照漂亮、实播 2~3 次/110s 重缓冲」的 720p 源——**探测快照无法感知实播表现**，这是排序的盲区。

### 4.1 方案（`d0e87b6`）

- `SourceProfile.stalls` 新列（缓存 8 列格式，兼容读旧 7 列）：播放中 **READY → BUFFERING** 换向按 URL 计数（初缓冲 / 换台重置不误计）；
- **探测排序**：stalls 紧跟 tinyWindow 之后降权；探测重建画像时显式携带 stalls——快照重建不能洗白已定罪源；
- **换台自动换选**：当前源 stalls ≥ 2 且存在更干净的同频道备选 → 起播前换选（日志 `prefer stall-free source`）。

### 4.2 闭环验证（定向列表，小米电视真机）

```
22:50:32  play 河南卫视 offset=6120ms      ← 720p 源（探测排序首选）
22:50:55 ~ 22:51:46  stall #1/#2/#3 noted  ← 110s 三次重缓冲全部被归因
22:52:36  play CCTV1（60s 零事件）
22:53:48  prefer stall-free source #1 (current has 3 stalls)  ← 自动换选
          play 河南卫视 offset=11120ms     ← 切到干净源
22:53:48 → 22:55:38  110s：零重缓冲、零掉帧、零报错
```

22 次快速换台（含起播期状态变化）零误计。同一轮终验中 CCTV1（116s）/ CCTV13（108s）+ 快速走过的约 20 个央视频道全部零重缓冲、零掉帧、零错误。
